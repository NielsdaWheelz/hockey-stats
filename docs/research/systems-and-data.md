# systems and data research

researched 2026-09-29. these are candidate boundaries and requirements for discussion, not architecture decisions. repository inspection is pinned to legacy commit `1d45312ed4a2d797150e377c87ecdba231b5ebfc`. the subsequent [brief](../brief.md) accepts effect application/python numerical ownership and records the user's other settled choices; the exchange mechanism remains open.

## judgment

the durable asset is an intelligible chain from source evidence to published claim. effect can make resource ownership, failures, and application contracts explicit. python can provide the numerical and statistical environment. neither language makes an inference valid or turns a transformed payload into source evidence.

the smallest defensible candidate is a batch data producer and a read-oriented website, connected through versioned artifacts. the producer owns hockey semantics: normalization, exclusions, features, models, and analytical outputs. the website owns requests, presentation, interaction, and visible explanations of coverage and uncertainty. ingestion ownership remains open until the old pipeline audit is complete; forcing a proven component into another language would need an actual benefit.

## what the old pipeline actually establishes

the strongest salvageable ideas are capture before interpretation, a shared offline derivation path, explicit missingness, and named hockey edge cases. the implementation does not consistently satisfy its own capture invariant.

`fetchJson` applies a projection before constructing the value later stored as raw. boxscores are flattened; roster records are filtered and augmented; reference records are filtered. therefore those stored bodies cannot establish what the upstream response actually contained. [fetch boundary](https://github.com/NielsdaWheelz/hockey-stats-legacy/blob/1d45312ed4a2d797150e377c87ecdba231b5ebfc/packages/core/src/ingestion/source-adapter/port.ts#L133), [production projections](https://github.com/NielsdaWheelz/hockey-stats-legacy/blob/1d45312ed4a2d797150e377c87ecdba231b5ebfc/packages/core/src/ingestion/source-adapter/port.ts#L487).

worse, `augmentRoster` manufactures a name and `shootsCatches: "L"` when a dressed player lacks a complete roster record. the committed supposedly live baseline contains 15 such rows. an unknown attribute becomes an asserted hockey fact. this is evidence against wholesale pipeline reuse, not evidence that every historical row is wrong. [augmentation](https://github.com/NielsdaWheelz/hockey-stats-legacy/blob/1d45312ed4a2d797150e377c87ecdba231b5ebfc/packages/core/src/ingestion/source-adapter/live-projection.ts#L146).

the fixture corpus is approximately 1.26 mb: 11 curated games, only one marked live, plus a failure-injection game. the manifest lists 79 files. the live classification applies to the game even though several constituent files are transformed. synthetic legacy html exercises an idealized parser contract. expected snapshots are generated by the decoder under test, making them regression baselines rather than independent correctness evidence. [fixture explanation](https://github.com/NielsdaWheelz/hockey-stats-legacy/blob/1d45312ed4a2d797150e377c87ecdba231b5ebfc/packages/core/fixtures/README.md), [snapshot generator](https://github.com/NielsdaWheelz/hockey-stats-legacy/blob/1d45312ed4a2d797150e377c87ecdba231b5ebfc/packages/core/src/testing/live-capture/regenerate-expected-snapshots.mjs#L64).

retain the case catalogue. retain play-by-play and shift captures as provenance-qualified candidates. audit downloaded data when the drive returns. do not promote projected fixtures into untouched source evidence. follow-ups: [raw provenance](../issues/legacy-raw-provenance.md), [fixture fidelity](../issues/legacy-fixture-fidelity.md), [external inventory](../issues/external-data-inventory.md).

## public implementations worth studying

[hockeyr](https://github.com/danmorse314/hockeyR) documents the 2023 api replacement and separates downloadable season data from fetching. its [game parser](https://github.com/danmorse314/hockeyR/blob/master/R/scrape_game.R) exposes substantive conventions: blocked-shot ownership is changed to the shooting team; coordinates are transformed; situations distinguish skaters and goalies; same-time events receive explicit ordering before shift reconstruction. these are analytical decisions, not cosmetic cleaning. its [shift parser](https://github.com/danmorse314/hockeyR/blob/master/R/get_game_shifts.R) also documents ancestry through evolving hockey and manny perry. borrow questions and attributable methods; verify conventions against actual cases before copying them.

[fastrhockey's current data repository](https://github.com/sportsdataverse/fastRhockey-nhl-data) separates raw collection, compilation, and published datasets, with a python implementation. useful ideas include bounded processing and inspectable artifacts. however, the inspected [season reader](https://github.com/sportsdataverse/fastRhockey-nhl-data/blob/main/python/nhl_data_build/season.py#L45) silently skips unreadable or invalid json; its [compiler](https://github.com/sportsdataverse/fastRhockey-nhl-data/blob/main/python/nhl_data_build/build.py#L29) reconciles schema drift with relaxed concatenation. those conveniences need explicit coverage accounting and schema policy before adoption here.

[hockey-scraper](https://github.com/HarryShomer/Hockey-Scraper) is explicitly unmaintained and licensed under gpl-3.0. treat it as historical method evidence, not an assumed maintained dependency. [the nhl api reference](https://github.com/Zmalski/NHL-API-Reference) identifies itself as unofficial. an endpoint catalogue is useful discovery material; it does not establish an upstream compatibility commitment.

## effect and the language boundary

on the research date, the [npm registry](https://registry.npmjs.org/effect) reported `latest: 3.22.2`, `rc: 4.0.0-rc.118`, and `beta: 4.0.0-beta.107`. the [official august recap](https://effect.website/blog/effect-v4-rc-august-recap) confirms v4 reached release-candidate status. calling the current work merely “v4 beta” is stale. the [release announcement](https://effect.website/blog/releases/effect/40-beta) explains ecosystem consolidation and that `effect/unstable/*` modules have weaker compatibility guarantees. recheck the registry at the implementation gate.

frontend support is concrete: the official [react atom package](https://github.com/Effect-TS/effect/blob/main/packages/atom/react/README.md) supplies reactive bindings and hydration helpers. its current installation targets the release candidate. this establishes feasibility, not a requirement to express every component or local interaction through effect.

candidate contract: python produces validated analytical artifacts; effect consumes them through explicit schemas. small response payloads can use json; larger analytical tables can use parquet, which [duckdb can query directly](https://duckdb.org/docs/data/parquet). the contract must define units, nulls, identifiers, exclusions, ordering where meaningful, and artifact versions. “both sides parse json” is insufficient.

avoid duplicate implementations of hockey formulas across languages. start with a command or batch boundary if that meets the eventual product requirements. a permanent python service needs justification from interactive computation, latency, or independent operation. effect's [json schema support](https://effect.website/docs/v3/schema/json-schema) may help express portable shapes, but shared shape validation cannot establish identical scientific semantics.

## provenance and correction requirements

proposed invariants:

- retain original response bodies before parsing or filtering, with source locator, retrieval time, status, and content hash. mark transformed and synthetic artifacts separately.
- keep source observations distinct from inferred facts and model estimates. missing handedness, coordinates, or shifts remain explicitly unknown unless an attributable derivation supplies them.
- identify an analysis by its selected input captures, transformation revision, configuration, and model artifact. “latest available” is a selection policy, not a reproducible input identity.
- distinguish refreshing sources, re-deriving from fixed captures, training, and publishing. repeating a derivation must not silently fetch newer inputs.
- publish a coherent completed artifact set. a failed rebuild leaves the previous usable set available; rollback selects that earlier set.
- record excluded games and records with reasons. successful execution with silently reduced coverage is not equivalent to a complete dataset.

these requirements do not imply a distributed workflow engine or a bitemporal database. a manifest and explicit batch commands may satisfy them. distinguish game time from retrieval time: newly downloaded historical data cannot automatically reconstruct what was known before a past game.

## offline evidence and explicit tradeoffs

the fixture set should combine untouched captured responses, small synthetic cases with hand-checked expected facts, and a compact derived dataset for the website. label origin per artifact. include only cases needed by supported behavior: same-second events, overtime versus shootout, goalie pulls, blocked shots, missing coordinates, and shift boundaries are strong initial candidates. synthetic cases test controlled semantics; real captures test external compatibility. neither substitutes for the other.

ordinary development must work without the drive or network. full-data jobs should explicitly require the external dataset and report its absence. silently replacing it with fixtures would falsify the meaning of a successful run. fixture size follows useful coverage, not a decorative game count; it is not a training or evaluation sample.

tradeoffs remain open: two languages buy numerical tools at the cost of a serialization contract and two environments; v3 buys stability while v4 avoids a later migration but accepts prerelease change; batch artifacts simplify reproduction while limiting arbitrary live computation; exact captures consume storage while preserving repairability. none warrants queues, clusters, a feature store, orchestration services, or elaborate plugin interfaces before demonstrated need.

before architecture, settle the first analytical question, supported seasons and situations, historical versus live freshness, and whether users need arbitrary recomputation or published analyses. those answers determine the system; a preferred framework does not.
